## Database and account security

The migration creates profiles, institutions and registration/verification records, scoped memberships and roles, programme/level references, student enrolments, tutor authorizations, reusable official institutional records, record change history, staged imports, setup tokens, invitations and audit events. ADM numbers and Tutor IDs are unique within an institution and account type. Identifier normalization applies NFKC, removes whitespace/hyphens and compares case-insensitively.

Institutional usernames never resolve to email in the browser. The `institutional-login` Edge Function performs exact scoped identifier lookup and forwards the password to Supabase Auth server-side. Supabase Auth identities use opaque `.invalid` synthetic email addresses for users without email; the address is private implementation detail and is never presented as a recovery channel.

Setup and invitation tokens are 256-bit random values. Only SHA-256 hashes are persisted. Tokens are single-use, expire after seven days, can be revoked, and are consumed under a database row lock. One-time setup links and invitations bind to an existing verified official record; activation copies the official name and academic assignments from that record. Institutional users create their own permanent password. An authenticated independent student can use an institutional invitation to link the same `auth.users` identity, preserving history.

The RLS model denies writes to roles, memberships, identifiers, tokens, invitations, rate-limit state, and audit records from ordinary clients. The migrations revoke default client grants on their tables before applying narrow grants, then rely on RLS for row scoping. Sensitive changes use server-side operations. Record corrections, record verification/setup-link issuance, invitation creation/revocation, institution profile/programme changes, catalogue changes, manual record creation, import staging/application, institution application submission/review, Tutor ID allocation, tutor authorization changes and recovery workflow status changes write audit events in the same database transaction as the corresponding database mutation. Recovery requests are recorded before Auth generates a link; successful issuance is recorded only after Auth returns a link, and failed generation is recorded as failed. Routine institution-admin recovery does not require global approval. Global admins can audit, escalate, and close exceptional recovery cases. Institutional directory lookup has a per-user, per-institution and trusted-proxy IP request limit. Public institutional login and invitation redemption use hashed identifier/token and IP failure buckets. Institution suspension and subscription/payment states remain separate concerns.

Recovery links are generated by Supabase Auth and are single-use. Their expiry follows the project’s configured Auth email OTP lifetime (Supabase documents a default of 3600 seconds); configure and verify the staging value before use. This implementation does not claim to revoke an already generated Auth recovery token individually because the current Auth integration exposes no per-link revocation operation. A suspected or disputed case is escalated and audited by a global administrator; handle user sessions through the approved account-security process.
